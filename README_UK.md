# zvolrescue-testdata

Тестові дані для [zvolrescue](https://github.com/click0/zvolrescue),
інструмента відновлення zvol-ів із ZFS у режимі лише читання. Тут живе
те, що [SPEC §9.1](https://github.com/click0/zvolrescue/blob/main/docs/SPEC.uk.md)
zvolrescue називає золотим образом і матрицею пошкоджень:

* **один золотий образ пулу** — один пул із top-level vdev-ами mirror,
  RAIDZ2 і dRAID1, zvol-и, знімки, клони, шифровані dataset-и, усі
  контрольні суми й стиснення, gang-блоки, сотні TXG — зібраний один раз
  скриптом у віртуалці зі справжнім ядром і далі незмінний;
* **оракул** — SHA-256 кожного тома на кожному знімку, вивід `zdb` для
  кожного TXG і члена, ключі: те «як має бути», з яким порівнюється кожне
  відновлення;
* **маніфести пошкоджень** — декларативні описи, що перезаписати (член,
  діапазон байтів, шаблон); прикладаються до тимчасових копій під час
  тесту, поодинці й у комбінаціях.

Відновлення можна тестувати лише тоді, коли правильна відповідь відома
наперед. Різноманіття тут іде від видів і комбінацій пошкоджень, а не від
кількості образів з іншим вмістом.

## Що тут зараз

**`image-v1`**, золотий образ, зібраний ядром: один пул `golden` із
top-level vdev-ами mirror-2, raidz2-4 і draid1 з `ashift` 12, дванадцять
томів по всіх контрольних сумах, стисненнях і трьох розмірах блока, клон,
шифрування raw-ключем і passphrase, знімки після кожного з дванадцяти
раундів записів, перейменування, знищення, форсовані gang-блоки, 5015
TXG — зібраний скриптом `tests/golden/build-image.sh` із zvolrescue на
OpenZFS 2.4.1 runner'а GitHub `ubuntu-26.04` (завдання `golden` у
`realworld.yml`), описаний в [IMAGE.md](IMAGE.md). Його оракул — в
`oracle/golden/`; матриця пошкоджень проти нього, прогнана на тому ж
ядрі одразу після збірки, — у
[reports/image-v1](reports/image-v1/README.md): 41 маніфест, 35 пройдено,
6 незастосовних, жодного поза очікуваною категорією. Першу його збірку
zvolrescue v0.9.8 відкинув цілком, бо не знав `dynamic_gang_header`;
v0.9.9 її читає.

Файли членів — це реліз `image-v1` тут: двадцять файлів `zstd`, десять
членів і узгоджена копія кожного після 6-го раунду заповнення (патерн
«старіша копія себе» в маніфестах), із `SHA256SUMS`; суми нестиснених
членів — в `oracle/golden/members.sha256`. Опубліковано
`publish-golden.yml` із zvolrescue з того прогону, що образ зібрав і
перевірив, ніколи руками.

До нього був **`image-v0-ztest`**, зібраний лише userland-частиною
OpenZFS (`ztest` + `zdb`, без модуля ядра, без root, без дисків): три
пули — mirror, raidz2, draid1 — зі справжніми метаданими ZFS, але без
zvol-ів. Він лишається: оракул в `oracle/mirror/`, `oracle/raidz2/` і
`oracle/draid1/`, опис у
[reports/image-v0-ztest/IMAGE.md](reports/image-v0-ztest/IMAGE.md),
члени — у релізі `image-v0-ztest` (суми в `oracle/SHA256SUMS-release.txt`),
а матриця проти нього — у
[reports/image-v0-ztest-r2](reports/image-v0-ztest-r2/README.md): 44
маніфести на трьох пулах, 112 застосовних прогонів, усі пройдено, один
дефект знайдено й виправлено дорогою (`--assume-member` відповідав «no
scanned pool is missing a member» про пул, якому бракувало цілого
top-level vdev). [Перший прогін](reports/image-v0-ztest/README.md)
лишено як запис; його стовпчик draid1 судив пул за його запасними
дисками, а не за членами, і не рахується. CI zvolrescue і далі збирає
один його пул для закріпленої підмножини матриці на кожному пуші.

## Структура

| Шлях | Що |
|---|---|
| GitHub Releases | члени образу, стиснуті `zstd`, по файлу на кожен, плюс `SHA256SUMS` — ніколи в git |
| `oracle/<пул>/` | інвентар dataset-ів, зняття `zdb`, мітки, layout, ключі — записана істина кожного пулу |
| `reports/<тег>/` | прогони матриці пошкоджень: що пройшло, що ні, що не застосовне |
| `manifests/` | маніфести пошкоджень, по файлу на клас і на набір комбінацій; формат у [manifests/README.md](manifests/README.md) |
| `IMAGE.md` | як зібрано поточний образ (скрипт живе в zvolrescue), версії інструментів, розкладка пулу, історія TXG; копія для давнішого образу лежить під його `reports/<tag>/` |

## Версіонування

Кожна версія образу — тег релізу тут (`image-v1`, `image-v2`, …);
zvolrescue фіксує тег і `SHA256SUMS`, які очікує. Образи ніколи не
правляться руками: зміна означає нову збірку і новий тег. Маніфести й
оракул версіонуються в git поруч.

## Чому не в git

GitHub обмежує файли в репозиторії до 100 MiB, а трафік Git LFS
тарифікується; реліз-артефакти дозволяють 2 GiB на файл і не лічать
завантаження. Члени образу добре стискаються (невикористаний простір — нулі),
тож реліз важить кілька сотень MiB. CI zvolrescue завантажує артефакти
один раз і тримає їх у кеші Actions.
